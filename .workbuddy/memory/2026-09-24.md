## 星间飞行：展开弹射叠加「星位等级」加成（StarMarkRules.java）

需求：目标（被弹方）星位等级越高，弹开的飞行距离越远。

**改动（全在 `technique/skill/StarMarkRules.java`）**
- 新常量 `BURST_STACK_BONUS = 0.25`；新方法 `burstStackScale(int stacks)` = `1 + BONUS × (等级-1)`，夹在 `1 ~ StarMark.MAX_STACKS(5)`。
- `burstNeighbors` 里 `burstImpulse(radius)` 改名 `baseImpulse`，实际初速改成**每对现算**：
  `double impulse = baseImpulse * burstStackScale(mover.mark().stacks());`
  —— 必须移进内层循环，因为等级是**逐标记**的，不能像半径那样在外层算一次。
- 倍率：1 级 ×1.00 → 5 级（叠满）×2.00。与半径项**相乘**，互不覆盖。

**为什么只乘初速、不乘上抛**：`BURST_LIFT` 固定 ⇒ 滞空时长恒定 ⇒ 位移严格正比于初速。「星位越高飞越远」= 抛物线原样拉长（弧高不变、落点更远），与既有「域尺寸只影响发射初速」的口径完全一致。**不要**顺手把 `BURST_LIFT` 也乘上去，那会让弧线变高而不是变远。

**关键事实**：等级无需自己算衰减——`StarMarkSkillLogic.resolveAll` 已对每条标记调 `StarMarkRules.decayedStacks` 并 `withStacks` 回写，所以 `ResolvedMark.mark().stacks()` 就是**结算衰减后的当前等级**（衰减最低 1 级）。旧存档缺 `lastMarkedAt` 读作 0 ⇒ 等级直接落到 1 级 ⇒ 弹得最近，安全。

**静态自查**：`impulse` 局部变量作用域确认（外层 `baseImpulse`、内层 `impulse` 无重名冲突）；`StarMark` 已 import（:5）、`MAX_STACKS` 为 `public static final int`；`burstStackScale` 调用点 1 处。**未跑编译**。

**未做（等用户定）**：lang 描述（`skill.jujutsukaisenzone.love_rendezvous_star_gate.desc`）没写这条；`burstNote` 计数后缀未加等级信息。

## 星间飞行：「踢足球」制导（StarMarkRules.java）

需求：被弹飞的目标进入**另一颗同类星**的吸引范围后，获得一份制导辅助；且**飞行速度越大制导越不明显**（设计决策点，用户明确否掉了「涌现」的说法）。玩家用星域尺寸 + 星位等级自己选"射门力度"。

**改动（全在 `technique/skill/StarMarkRules.java`）**
- 新常量 `GUIDANCE_IMPULSE = 0.045`；新 helper `isAirborne(ResolvedMark)` = `entity != null && !entity.onGround()`。
- `apply` 同星吸引的**成员循环**内现算：`if (!pullThisGroup && isAirborne(member)) { memberStrength += GUIDANCE_IMPULSE; memberVertical = 0.0D; }`，并把 impulse 改用 `memberStrength` / `memberVertical`。
  ⚠️ **必须挪进成员循环**：`strength` / `verticalScale` 是**组级**的（组循环外一次定下），而"在不在飞"是**成员级**的。第 757 行起的 for 循环。
- 不动 `apply` 其余结构、不动弹射。

**⭐ 两条设计约束（写进常量 Javadoc，防后人"优化"掉）**
1. **必须用「加力」而不是「转向」**：横向冲量恒定 ⇒ 偏角 `atan(横向/前向)` 随速度下降 ⇒「飞得越快越难命中」**免费**得到；若改成固定转向速率，速度再高也照转，就得手写衰减去补。物理类比 = 弧线球（横向风力固定，球速越快弧线越不显）。
2. ⛔ **绝不允许乘 `burstStackScale` / `burstImpulse`**：制导是**固定额度**补偿。一旦跟速度同步放大，满级星飞 2 倍远、补偿也 2 倍 ⇒ 容错占比不变 ⇒ 难度梯度当场抵消。这是设计决策，不是遗漏。

**关键事实**
- **触发条件不用写代码**：`ATTRACT_RANGE = 16` 就是"进入吸引范围"，同星吸引组本来就要求同星 ≥2 条、逐帧按距离判定。⇒ **不需要"发射时记目标 + 开窗口"的状态机**。
- **落地即结束制导**（`!onGround()`），覆盖"弹飞后那一段"，无窗口状态、发射方不用记账。
- **垂直分量清零**：留着 `ATTRACT_VERTICAL_SCALE=0.35` 会让空中的球被地面目标往下拽 ⇒ 滞空变短、落点提前。清零后弧线高度只由 `BURST_LIFT` 决定，落点仍只由水平速度决定。
- 方向：同星**恰好两颗**时质心方向**精确指向对方**（无偏差，只是幅度不够）；三颗以上分散两侧会互相抵消（既有设计，别改）。方块锚点也是同星组成员 ⇒「立一颗同星方块当球门」自动成立。

**数值（半径 8 档、滞空约 10 tick、行程 ≈ 速度 × 6.8）**：制导侧移约 1.6~1.9 格 ≈ **2 格容错窗口**（猪碰撞箱约 0.7 格宽）。1 级 1.40 / 行程 9.5 格 → 占比 20%；5 级 2.80 / 19 格 → 10%。**跨度约 4.6 倍**（0.60~2.80）。实际力度还要乘 `(0.35 + falloff)`，16 格处只有 0.35 倍。

**已知闸门（非 bug，别顺手改）**：`MIN_SEPARATION=1.5` 内侧吸引松手 ⇒ 最后半格无制导（正好保证"不是必中"）；`ATTRACT_RANGE=16` 是制导射程；`MAX_SIMULATED=16` 截断 ⇒ 标记多于 16 条时最远那几条完全不参与力学，也就没有制导。创造/旁观玩家与玩家本体照旧不吃力（`push` 早退）。

**静态自查**：`GUIDANCE_IMPULSE` / `isAirborne` 各 1 处定义 1 处调用；`memberStrength` / `memberVertical` 局部无遮蔽；`strength` / `verticalScale` 仍被用于初始化，无未使用变量；`Entity#onGround()` 全项目已有 3 处调用可佐证 API。**未跑编译**。

## 星间飞行：撞击伤害（`resolveImpacts`）——「踢足球」的收益点

用户定性：**踢足球不是玩法而是「造成伤害的方法」**。常态同星相吸只是每 tick 0.010 的力、缓慢靠近，撞不痛；只有弹射那种力道才谈得上撞击 ⇒ 速度同时管三件事：飞多远、好不好打准、撞上去多痛。

**改动（全在 `technique/skill/StarMarkRules.java`）**
- 新常量：`IMPACT_DAMAGE_PER_SPEED=12.0`（伤害 = 撞击速度 × 此值）、`IMPACT_MIN_SPEED=0.45`、`IMPACT_MARGIN=0.35`、`IMPACT_COOLDOWN_TICKS=10`、`BURST_FLIGHT_TICKS=40`。
- 新实体键（**注意：挂在实体身上，不是玩家数据**）：`TAG_BURST_UNTIL`（到期刻）、`TAG_IMPACT_AT`（上次撞击刻）。Forge 会把实体 `persistentData` 存成 `ForgeData` 落盘。
- `burstNeighbors` 里推出去的同时盖 `TAG_BURST_UNTIL = now + 40`。
- 新方法 `resolveImpacts(owner, marks)` + `horizontalSpeed(Entity)`；在 `apply` 里于**同星吸引组循环之后、跨序块之前**调用，且刻意传**完整 `marks`**（不是 `simulated`——球往远处飞，按「离施术者最近」截断到 16 条最可能把球剔掉）。
- 伤害走 `TechniqueDamageSources.deal(target, owner, amount)`（**符合项目铁律，不许写 `damageSources().magic()`**），双方各一记，用 `|` 不用 `||`（短路的会跳过第二记）。

**⭐ 关键技术点：必须扫掠，不能逐点判定**
实体之间原版不做碰撞（会互相穿过），而球速可达 **2.8 格/tick**、猪只有约 **0.7 格宽** ⇒ 每 tick 取一个点判，高速球直接「跳」过目标，**越用力越打不中**（与设计意图相反）。解法：`victim.getBoundingBox().inflate(0.35).clip(tail, head)`，其中 `tail = head.subtract(ball.getDeltaMovement())`——**tick END 时 `getDeltaMovement()` 就是本 tick 实际位移**（`Entity#move` 内部会 `setDeltaMovement` 回写），所以线段即「上一刻→这一刻」。
已核对 1.20.1 源码 jar：`AABB#clip(Vec3,Vec3)` → `Optional<Vec3>`（AABB.java:271）、`AABB#inflate(double)`(:188)、`Entity#getBoundingBox()` 是 `public final`(:2765)、`onGround()`(:608)、`getDeltaMovement()`(:3182)、`LivingEntity#getMaxHealth()`(:1655)。⚠️ `AABB#intersects(Vec3,Vec3)`(:232) 是**两点式**，不能当线段用。

**判定条件三件套**：① 球有未过期的 `TAG_BURST_UNTIL`（⇒「缓慢靠近不痛」由标签精确保证，不是靠猜速度）② 水平速度 ≥ `IMPACT_MIN_SPEED`（同星吸引稳态漂移仅 0.11，永远够不到）③ 扫掠命中。

**边界（刻意，非 bug）**：方块（无实体）与掉落物（非 `LivingEntity`）不参与 ⇒「立一颗同星方块当球门」只负责吸引瞄准、撞上零伤害；未被标记的目标不结算；一颗球一次只撞一个目标（`break`）；**多玩家同时标记同一实体时，`TAG_IMPACT_AT` 在球身上 ⇒ 跨施术者天然去抖，不会双倍伤害**。

**伤害数值**：速度 1.4 → 17 点；2.8 → 34 点；阈值边缘 0.45 → 5 点。猪(10血)一击毙；玩家(20血)挨重炮大半条。**不需要再乘星位倍率**——速度已含 `burstStackScale`。

**未做/待定**：施术者本人的自身标记作为**被撞方**时也照规则受伤（`deal(player, player, ...)` 自伤）——已告知用户，一行可豁免；lang 未写；`burstNote` 未加伤害信息。

**静态自查**：新符号定义/调用点齐全（`resolveImpacts`:966 调用、`horizontalSpeed`:614、`AABB`+`TechniqueDamageSources` import 已补）；`ballLiving` / `living` 模式变量作用域与确定赋值成立；`Math.round(float)→int`；**未跑编译**。

## 「飞行，穿越」· 星域内「依次穿越」折线版

需求：在自己星域中施放时，先按星序依次穿越**这一轮已解锁的星位**（每位取最近的已标记目标——实体 / 方块 / 掉落物皆可，够不着就跳过），每穿一颗踢击 +40%、上限 +200%；全程对路径上的实体造成伤害与击退；穿完才追踪并踢击真实目标。

- ⚠️ **核心坑：通行证会被自己抹掉**。星位解锁进度存在 `TAG_GATE_UNLOCKS`（属于**那一轮星域**），而 `cast` 必然 `deactivateGate` → `resetGateUnlocks` 直接 `remove` 整份键。⇒ 位图**只能在关域之前读**。为此把 `StarMarkRules.unlockMaskOf` 由 private 提为 public。快照只存进 `Flight`（内存态）、**不落盘**——`FLIGHTS` 本来就不跨死亡 / 掉线 / 换维度，落盘只会留下永远读不到的死数据。
- 「在自己星域里」新增 `StarMarkRules.insideOwnGate` = 域生效中 **且** 站在任一域心半径内。跟随域圆心就是脚下（恒为真），所以这条真正过滤的只有「固定域留在别处、人已经走开」。
- **`Flight` 由单段改折线**：`List<Leg> legs`（`Leg` = `StarMark` + 可空 `Entity`，方块只有坐标）+ `index` / `passes` / `rammed`。`step` / `remaining` / `deadline` 改成**每段重挂**（`beginLeg`），总时长上限 = 段数 × `FLIGHT_TIMEOUT_TICKS`。
- ⚠️ **末段锚点必须与穿越段分开**：旧 `tick` 一律瞄 `living.position()`（脚下）。折线版若统一走 `anchorOf`（头顶之上），末段会悬在目标上方两格多才结算 ⇒ 落点手感回退。现在 `legAnchor(level, leg, last)`：`last` 取 `entity.position()`，非 last 取 `anchorOf`。

- **路径撞击 `ramPath`**：`new AABB(from, next).inflate(1.5)` **扫掠**（按当前位置点判定会让擦身而过变随机）；排除施术者 + `finalEntityId`（最终目标由踢击单独结算，不该在撞上前一 tick 先吃一记）；`Flight.rammed` 保证每实体整趟只打一次。伤害 `PATH_DAMAGE = 6`，击退走新增的 `StarMarkRules.flightRam`（= `push(burstKick(from, victim, 0.80))`，⚠️ **不盖 `TAG_BURST_UNTIL`**——路径撞飞 ≠ 当球资格，那是 `flightKick` 的特权）。

## 跨序斥力重做：芝诺墙（Zeno Wall）

用户报障：**生存模式下跨序之星仍能以极低速度一点点贴近，疾跑时斥力形同虚设**。要求设计「芝诺的乌龟悖论算法」。经核对，这**不是数值问题，是作用域用错了**。

### 根因（两条，都不是「力度不够」）

1. **速度域比不过持续输出**：旧斥力 = 每 tick `setDeltaMovement(dm.add(impulse))`，力度 `REPULSION_IMPULSE(0.075) × (0.30 + falloff)`，**上限 0.0975 格/tick**。对照僵尸寻路约 0.23、玩家步行约 0.11、疾跑约 0.28 ⇒ 净向内推进，于是「一点点贴近」。**调大也没用**：那只是比谁力气大，且会顺手把弹射类效果一起放大。
2. **对玩家基本无效**：玩家位置由**客户端权威**，服务端设的 `deltaMovement` 每 tick 被客户端移动包覆盖（与「飞行，穿越」必须用 `teleportTo`、「推力对服务端玩家无效」是同一根因）。`hurtMarked = true` 只让客户端接受**实体**运动包，对玩家自身的本地预测无感。

### 算法：约束位移，不约束力

芝诺悖论的数学本质是几何级数收敛。反过来用：让**朝内速率正比于剩余可接近距离**，即
`dd/dn = -k·(d - ZENO_CORE)` ⇒ `d(n) - ZENO_CORE = (d(0) - ZENO_CORE)·(1-k)ⁿ`，**指数逼近、永不归零**。

落地 = 每 tick 只放行 `zenoInwardCap(d)` 格朝内位移，超出的当场退回：

- `zenoInwardCap(d) = ZENO_INWARD_CAP(0.20) × u^ZENO_EXP(1.0)`，`u = (d - ZENO_CORE)/(REPULSION_RANGE - ZENO_CORE)`，`u` 在外沿为 1、到 `ZENO_CORE` 为 0。
- 卡点体感：d=6 → 0.200 格/tick；d=4 → 0.100；d=3 → 0.050；d=2.5 → 0.025；d→2.0 → 0。**任何速度都被免疫**，因为放行的从来不是速度，而是「这一 tick 允许靠近多少」。

### 三处必须记住的实现约束

- ⚠️ **`ZENO_CORE(2.0)` 必须 < `CONTACT_RANGE(2.5)`**。接触是跨序解锁的**唯一**达成方式，底线压到接触线之上 ⇒ 跨序链永远推进不了，「飞行，穿越」的依次穿越也一并锁死。留 0.5 格余量 = 「理论上够得着、但要龟速磨两三秒」，恰好保留「逐级经过」的可玩性。
- ⚠️ **限速绝不能加到通用 `push` 上**。`flightKick` / `flightRam` / `burstKick` 都走 `push` 且 1.40 起步，被 0.20 的上限削一刀就直接哑掉。所以另开入口 `zenoWall`，只在跨序段调用。
- ⚠️ **基准必须先登记、后判定跳过**。`ZENO_LAST_POS` 是 `WeakHashMap<Entity,Vec3>` 的位移快照；若把 `put` 放在各种 early-return 之后，一颗球飞满 40 tick 落地后，下一 tick 会拿它跟 40 tick 前的旧快照相比、凭空虚算出好几格位移，于是当事人被一记 1 格（`ZENO_MAX_CORRECT` 顶格）的莫名推力掀一下。

### 其他落点决策

- **落点两分**：mob / 其他实体位置服务端权威 ⇒ `setPos`；**玩家必须 `teleportTo`**（唯一能压住客户端权威的手段），且只在 `inward > allowed` 时才发位置包，减少 90% 的带宽与回拉。
- **只算水平**：竖直一概不碰。沿三维修正时，悬停的星（恶魂 / 幻翼）会把正下方的玩家往地里按，修正与碰撞互相打架。两侧水平完全重叠时（`flat.length < 1e-6`）直接跳过。
- **两道豁免**：`TAG_BURST_UNTIL` 未过期的球（削位移会把「星星大碰撞」的抛物线压平）、`StarFlightSkillLogic.isFlying` 的施术者（那段位移是脚本化的，两者同时改位置会互相覆盖；穿越途中星域已收，本属防御性判断）。
- **删除的常量**：`REPULSION_IMPULSE`、`REPULSION_VERTICAL_SCALE`（后者是纯竖直力的产物，位移约束下不再需要）。`REPULSION_RANGE` / `MIN_SEPARATION` / `ATTRACT_VERTICAL_SCALE` 仍在使用。
- 类头 javadoc 的「三条实现纪律」第一条已加例外说明：**唯跨序斥力不用增量速度**。

**静态自查**：`REPULSION_IMPULSE` / `REPULSION_VERTICAL_SCALE` 全库无残留；`ZENO_*` 定义 4 处 / 引用点逐个核对；`REPULSION_RANGE` 仍被范围闸与 `zenoInwardCap` 使用；`MIN_SEPARATION`(吸引段) / `ATTRACT_VERTICAL_SCALE` 仍在用；`WeakHashMap` import 已补；`StarFlightSkillLogic.isFlying(ServerPlayer)` 签名核对（`:213`）；`ServerPlayer#teleportTo(double,double,double)` 与 `Entity#setPos` 用法与库内既有代码一致。**未跑编译**（IDEA 由用户跑）。

## 14:04 芝诺墙二次修复：跨序之星仍能「磨蹭着接触」

**症状**：实体间表现正常，但玩家走向「跨序之星的草方块」时能磨蹭着贴上去。

**根因一：核心距离落在接触线以内。** `ZENO_CORE` 原为 2.0，而 `CONTACT_RANGE = 2.5` —— 墙把双方锁在「锚点距离 2.0」，而 2.0 早已在接触圈内。玩家每 tick 净推进 `zenoInwardCap(d)` 格（d=2.5 处为 0.025 格/tick），约 7 秒就能从外沿磨到接触线。

⚠️ 上一轮写的「`ZENO_CORE` 必须 < `CONTACT_RANGE`，否则跨序链锁死」**论证是错的**：接触判定要求「对方那颗星本来就在自己的位图里」（`effectiveMask`），也就是这一侧本来就不吃墙，所以「逐级经过」永远够得着目标；「飞行，穿越」的折线走 `planChain`，根本不经过接触判定。墙真正该封死的只有**被排斥的那一侧**。

**根因二：同一 tick 内多条跨序约束只有第一条生效。** 旧实现开头 `put(entity, current)`、修正后又 `put(entity, corrected)`。而 zenoWall 在同一 tick 里会被**每条跨序标记**各调用一次（域内有几颗跨序星就有几个方向），第二次调用时 `previous` 已是本 tick 刚修正过的位置 ⇒ `inward ≈ 0` ⇒ 第二条方向被静默吃掉。域内有多颗跨序星时，只要「正走向的那颗星排在列表后面」，朝它的墙就完全不存在。

**修法**：
- `ZENO_CORE` 2.0 → **3.0**（= 接触线 + 0.5）。接触判定读的是**修正前**的位置（锚点在 `resolveAll` 就算好），所以必须留「单 tick 位移」余量：疾跑跳跃水平位移约 0.36 格/tick，跨不过 0.5；能跨过去的只有碰撞击飞 / 爆炸 / 鞘翅俯冲那个量级。
- 位移快照一张表 → 三张表：`ZENO_PREV`（上一 tick 的**最终**位置，本 tick 只读）/ `ZENO_CUR`（本 tick 最新落点）/ `ZENO_TICK`（转正发生在哪个 tick）。进入新 tick 时先把 `ZENO_CUR` 转正进 `ZENO_PREV`，此后基准本 tick 内不再变 —— 第二条约束读到的是「本 tick 累计靠近量」，多个方向于是**自然累加**。落点更新放进 `try/finally`，保证被跳过的分支（创造模式 / 正在飞的球 / 正在穿越的施术者）也推进基准，否则快照僵住 → 下一 tick 凭空虚算位移 → `ZENO_MAX_CORRECT` 顶格乱推。
- 连带改了 `ZENO_INWARD_CAP` 的注释（圈厚从 4.0 变 3.0，拖拽手感更陡）。

**静态自查**：`ZENO_LAST_POS` 全库无残留（grep 只剩 `ZENO_PREV`/`ZENO_CUR`/`ZENO_TICK`）；`Long recorded` 用 `longValue()` 比较、`put(entity, now)` 自动装箱；`settled` 局部变量无 lambda 捕获、可在 try/finally 中赋值；多方向累积的前提「`position()` 在 `teleportTo`/`setPos` 后立即反映修正」成立。**未跑编译**。

**待用户确认**：若是在**创造 / 旁观模式**下测试，玩家本来就被显式豁免（`zenoWall` 开头 `isSpectator() || isCreative()` 直接 return），需在生存模式验证。

## 领域「爱与幽会」机制评审（用户提问，本轮未改代码）

**总判断**：意象准（域内所有标记「上膛」+ 双星相撞双双炸开），但**去掉的摩擦多于加上的玩法** —— 域内近似「同一套玩法的无敌版」，而不是「另一套玩法」。

**三个待决点**：
1. **引爆的代价被抹掉，但收益翻倍。** `StarMarkDetonation` 的 dok 明确写「引爆是前置成本最高的动作：叠满 5 级约 150 咒力 + 时限压力，且清空层数必须从头再叠」。领域「每 5 秒点满」把这层门槛直接取消；而 `resolveImpacts` 里是**双方各引爆一次**（球 + 目标各吃 22 + 各自撞击伤害）⇒ 一次成功撞击 ≈ 每个目标 40+ 伤害。领域维持是固定开销（`MAINTAIN_COST_BASE_PER_SECOND + radius × …`），**边际成本为 0**，只在 5 秒上节流。
2. **制导连玩家的选择权一起拿走了。** `nearestStrikeable` 自动选最近目标，**不筛星种、不筛敌我**；且 `nearestStrikeable` 与 `resolveImpacts` 都**只排除 `ball` 自己、不排除施术者** ⇒ 施术者若 Shift 给自己打过标记（官方支持，且能引爆自己），域内球会**主动追着他撞**并造成撞击自伤（引爆侧 `damageCore` 是豁免 owner 的，撞击侧不豁免）。域外这是偶发，必中把它变成必然。
3. **只覆盖「星位 / 碰撞」，对「跨序」零提及。** 域内球因 `TAG_BURST_UNTIL` 豁免芝诺墙，但**施术者本人仍受墙约束** —— 与「必中」的宣言不一致；且「点满星位」对跨序位图（接触驱动、10s 限时、独立状态）完全无效。跨序是这套术式最有辨识度的机制，域内却变得无关紧要。

**改进方向（未采纳，供后续讨论）**：
- a) 引爆后该标记进入 5 秒「不可被点满」冷却 —— 把代价还回来，保留满级作为常态但让引爆重新成为有节奏的动作。
- b) 制导尊重玩家意图：只锁「选中的星种」或视线方向的目标，而不是最近的那个。
- c) 域内**直接取消芝诺墙** ——「爱与幽会」= 距离与顺序都不重要。一句话把两套机制缝上，跨序就不再显得多余，领域也有了真正的「改写规则」宣言。

## ⭐ 设计方向澄清：用户要的是「连锁反应」（对标原神达达利亚断流）

**用户原话**：「其实我是想做那种连锁反应机制的，目前确实做得有些过了，参考原神达达利亚的被动。」⇒ 承认「每 5 秒全域点满」过头，真正想要的是**有源的传播链**。

### 达达利亚「断流」的准确结构（已联网核实）
- 断流是**开关式状态（有 / 无），不是累积式资源**。基础 10s，天赋「永无谢幕」→ 18s；重复施加 = **刷新持续时间**。
- 上标记：蓄力瞄准射击 / 天赋「水形剑」(近战暴击) / 远程大招魔弹一闪。
- 四种触发（按攻击方式）：断流·闪（远程蓄力，0.7s CD）/ 断流·斩（近战命中，1.5s CD）/ 断流·爆（近战大招，**消耗**标记）/ **断流·破**。
- ⭐ **断流·破 = 击败处于断流状态下的敌人 → 范围水伤 + 对附近的敌人施加断流**。官方攻略原话称其「实现了全自动断流的传染效果」。**连锁引擎就是它。**
- 连锁链：上标记给 A → 打 A → **击杀** A → 破：范围伤 + 给 B、C 上标记 → 打 B → 击杀 → 给 D、E 上标记 → …
- 链条能「连」的前提：断流是**开关式**，被传播到的 B、C **立刻就是可触发状态（零延迟）**。

### 对照他的系统：链条已经存在，断点在哪
- 他的链条：打标 → 叠 5 级 → 再叠一次 = 引爆（22 单体 + 半径 4 debuff + **传染干净目标到 1 级**）→ 对新目标叠 5 次 → 引爆 → …
- **`StarMarkDetonation.spreadMark` 就是他的「断流·破」**（半径 4 内、尚未持有任何标记的目标 → 打上同一颗星、1 级）。
- ⛔ **断点**：传染给的是 **1 级**，而引爆需要 **5 级** ⇒ 每一环都有「重新攒 4 次」的空白，链条延迟巨大，实际是「逐个清场」而非连锁。
- ⭐ **「每 5 秒全域点满」正是在补这个断点，但补过头了**：它让**还没进入链条的目标**也满级，等于**删掉了连锁的前提**（连锁的前提就是「标记靠传播获得」）。这是**无源预热**，不是**有源连锁**。达达利亚若全场敌人开局自带断流，也就没有连锁可言了。

### 正确改法（已提出，待用户确认后实施）
1. ❌ 删掉「每 5 秒全域点满」（定时脉冲 + 成形时那一次），`LoveRendezvousDomainExpansion` 的整个 `pulseRemainingByCaster` 计时机制随之作废。
2. ✅ **域内引爆的传染等级：1 级 → 满级** —— 一条改动即可把「逐个清场」变成「连锁」。
3. ❌ 去掉「撞击双方引爆」，**只引爆被撞的那一个**（球侧不炸）。双方各爆一次是「过」的地方。
4. ➖ **制导必中保留**。⚠️ 修正我上一轮的评审：在连锁框架下必中是**链条的可靠性保障**（每环都必须成功，靠运气命中链条会断），不是「抹掉操作」。
5. 🔁 意外收获：**引爆清空标记（`remove`）从「缺点」变成「优点」**——被炸过的地方变回干净目标，于是**可以被再次传染** ⇒ 链条天然可往复循环、不会枯竭。
6. ❓ 待用户定：是否让传染也覆盖「已有**同星**标记」的目标（刷新到满级）。达达利亚的重复施加 = 刷新持续时间；而现在 `spreadMark` 跳过一切已有标记，链条会在「周围都被标过」时枯竭。⚠️ 注意 `spreadMark` 里两条「收窄」（不覆盖已有标记 / 不作用于施术者）原本是**防止破坏星阵 + 防连锁失控**，在「要连锁」的前提下需要重新权衡。

## 新增机制：「引力弹弓」（域外专属）

**动机**：撞击结算只认 `LivingEntity` ⇒ 方块撞不出伤害，「球被同星吸向方块 → 停在旁边等标签过期」是条**死路**；`nearestStrikeable` 甚至刻意排除方块。本机制把死路改写成加速带。类比：球=航天器，同星方块=大质量天体。

**只有 `StarMarkRules.java` 一个文件**（+261 / −13）。新增常量：`SLING_RANGE=2.5` / `SLING_BOOST=0.6`(加法) / `MAX_BALL_SPEED=3.4` / `SLING_LIFT=0.30` / `SLING_MAX_PER_BALL=2`；标签 `TAG_SLING_USED`（球身 `long[]`，存 `BlockPos#asLong()`）。

**关键设计点**
- **域内/域外互斥分支**：`apply()` 里做成 `if (isRendezvousDomainActive) homeBalls(); else slingBalls();`——域内是「必中终结」（撞击即摘球身份、一颗球只换一击），与「续航」语义互斥，结构上就不能同时接管。
- **两道闸**：`SLING_MAX_PER_BALL` 限总量（防方块接力无限飞）+ 「同一方块只弹一次」（防球停在影响球内每 tick 重弹）。二者共用 `TAG_SLING_USED` 数组：长度即次数。
- **必须封速**：速度是伤害**唯一**乘数（`IMPACT_DAMAGE_PER_SPEED=12`），不封顶就是「一记即死」而非「更疼」。
- **`markAsBall` 顺手清账**：原两处直接 `putLong(TAG_BURST_UNTIL)` 收敛为一个助手（`burstNeighbors` / `flightKick`），同时 `remove(TAG_SLING_USED)`——同一只生物被反复踢（先展开弹开、再终结技），沿用旧账会借不到力。
- **`nearestStrikeable` → 拆出 `nearestStrikeableFrom(origin, exclude, marks)`**：两处口径共用（`homeBalls` 拿球位、`slingExit` 拿方块锚点当原点）。
- **`slingExit` 找不到下一个靶子时退回原航向**（只加速不改向）——返回零向量会让球当场停住，比不加速更糟。

**⚠️ 唯一待实测前提**：方块锚点在方块正上方 1.15 格（`BLOCK_MARK_HEIGHT`），球瞄的是这个空中点，「掠过不撞」在**锚点意义上**成立；但**原版物理碰撞仍在**——方块若为实心块、球又贴地飞，球箱会怼在方块侧面停住。需实机验证「掠过 vs 撞停」。

**自查（未编译）**：`StarMarkRules` 括号配平 OK（2141 行）；新标识符（12 个）全项目 grep 仅出现在本文件，零冲突；从 MC 官方映射源码 jar 核对 `CompoundTag.getLongArray(String)→long[]` / `putLongArray(String,long[])` / `BlockPos.asLong()→long` 三个签名（临时探针目录已删）；`Arrays`/`CompoundTag`/`StarMark` 三个 import 既有，无需新增。**编译待 IDEA**。

## 技能伤害分型（`SkillDamageType`）——只做归类，不做乘区

用户动议：把技能伤害分成 术式 / 体术 / 复合，供以后做更深的技能机制与伤害乘区。中途**主动收窄范围**：「不需要太复杂的系统，只是用在技能中，给技能的伤害类型划分用」⇒ 最终只落地**分类标记**，没做乘区管线、没注册 vanilla DamageType。

### 现状诊断（关键）
- 系统里原本**没有**「伤害类型」概念：体术身份靠 `EpicFightDamageSource.isBasicAttack()` 在 `BlackFlashEvents:114` / `:270`、`GavelWeaponEvents:94` **各自推断**；术式身份靠「不是 EF 源」反推。分类散落各处 ⇒ 乘区没地方挂。
- 基础值归属**不对称**：体术基础值归 EpicFight（只能乘），术式基础值归 `SkillCombatConfigRegistry`（能定）。
- 真正产生伤害的技能实体 8 个：7 个走 `TechniqueDamageSources.deal`，只有**法槌投射物**走 `damageSources().thrown()`。

### 落地（4 处）
1. 新增 `technique/skillset/SkillDamageType.java` — 枚举 MARTIAL / TECHNIQUE / COMPOSITE，带 `translationKey()` / `displayName()`，键前缀 `gui.jujutsukaisenzone.damage_type.`。
2. `TechniqueSkill` 加 `damageType` 字段 + getter + **11 参重载构造**；原 10 参构造委托给它并默认 `TECHNIQUE` ⇒ **20 处既有调用点零改动**。
3. `JudgmentTechniqueSkillSet` 的「法槌」显式标 `MARTIAL`（唯一非术式，判据 = 伤害通道）。
4. `zh_cn` / `en_us` 各加 3 个键（体术/术式/复合 · Martial/Technique/Composite）。

### 刻意不做的
- 不注册 `data/*/damage_type/`：体术那半的 DamageSource 类型归 EpicFight（自带硬直/冲击/破甲），替换会丢语义；`magic()` 的穿甲/抗性语义是 `TechniqueDamageSources` 明确要保持的 ⇒ 分型是**旁路标签**，不是替换 DamageType。
- 没做乘区链 / 没做 `DamageProfile` 权重向量（提过，被用户收窄掉了）。

### 待用户回话

## 更正：法槌投射物的归因**没有**问题（推翻上面「顺手发现、未动的隐患」一节）

上一条写「`GavelProjectileEntity:60` 没走 `TechniqueDamageSources.deal` ⇒ 法槌投射物击杀不给咒术经验、不掉术式情报、不记罪恶者、不判黑闪」——**是错的**。缘于「没走 deal ⇒ 一定没归因」的臆断，没读原版源码。用户据此要求修，查证后必须先更正。

### 实测（1.20.1 sources jar，`~/.gradle/caches/forge_gradle/.../*-sources.jar`）
- `DamageSources#thrown(direct, causing)` → `new DamageSource(type, direct, causing)`；`DamageSource#getEntity()` 返回的是 **causingEntity**。所以 `thrown(this, owner)` 的 `getEntity()` **就是投掷玩家** ⇒ `CursedGradeKillEvents#resolveKiller` 第一条判据 `getEntity() instanceof ServerPlayer` 直接命中；`TechniqueIntelligenceDropEvents:32`、`SinfulOneKillEvents:48` 读的也是 `getSource().getEntity()` ⇒ 全部正常。
- 爆炸段同样带归因：`Level#explode(Entity,...)`（`Level.java:510`）传 `damageSource = null` ⇒ `Explosion#getDamageSource()` 回退成 `explosion(getDirectSourceEntity() = 投射物, getIndirectSourceEntity() = 投射物.getOwner() = 玩家)` ⇒ `getEntity()` = 玩家。
- `LivingEntity#hurt` 1122~1134 行确认：`getEntity()` 非空即 `setLastHurtByMob` + `lastHurtByPlayer`。

### ⇒ 不能改成 `deal`，那是回归
1. `GavelWeaponEvents#isGavelWeaponDamage:82` 第一条判据是 `source.getDirectEntity() instanceof GavelProjectileEntity`；而 `deal` 刻意把 directEntity 填 **null**（为了盾牌挡不住术式）⇒ 法槌投射物对【罪恶者】的增伤会失效（第二条判据 `isWieldingGavel(player)` 在抛出后手上已无槌，兜不住）。
2. `thrown` 是物理投射物伤害（受护甲减伤、可被盾挡、带 0.4 击退）；`deal` 复用 `magic()` ⇒ 变成**无视护甲**。数值语义被直接改掉。

### 真正查到的问题（都不是归因）
1. **直接命中伤害被同 tick 的爆炸吞掉。** `onHitEntity` 先 `detonateAt` 再 `living.hurt`：爆炸先走 `else` 分支把 `invulnerableTime=20`、`lastHurt=爆炸伤害`；随后命中一击落入 `(float)invulnerableTime > 10.0F && !BYPASSES_COOLDOWN` 分支，`if (pAmount <= lastHurt) return false` ⇒ **直接返回 false**（连击退也跳过——`flag1=false` 同时跳过了 knockback 段）。爆炸量级 `Explosion.java:199` = `(int)((d10² + d10)/2 * 7 * f2 + 1)`，`f2 = power * 2`：标准 power 1.5 ⇒ f2=3、贴脸 d10≈0.7、`getSeenPercent` 近似 1.0 ⇒ 约 13；大锤 power 4 ⇒ f2=8 ⇒ 约 47。两者都远大于命中伤害（6 / 15）⇒ **「投掷伤害」实际恒为 0 效果**。
2. **爆炸会炸到投掷者自己。** `Explosion#hurtEntities` 只排除 `this.source`（投射物本身），`Entity#ignoreExplosion()` 恒 false 且 Player 无覆写 ⇒ 3 格（标准）/ 8 格（大锤）内的投掷者照吃；大锤贴墙扔 ≈ 47 自伤。

**处理决定（用户当日拍板）：两个问题都先不动。**「直接命中被爆炸吞掉」选择维持现状；「爆炸自伤」也选择保留（当作投掷武器的风险代价）。本轮**未改动任何文件**。留作后续：若哪天要让「投掷伤害」真正生效，走「爆炸排除被直接命中的目标」（`ExplosionEvent.Detonate` 过滤），而不是改结算顺序——顺序调换不改总量（同 tick 内恒为两者取大者）。

**给未来的自己：`thrown(x, owner)` 这类原版投射物源本身就带 causingEntity，归因是通的。**「必须走 `TechniqueDamageSources.deal`」这条铁律的真正理由是 `damageSources().magic()` 归因为 null，**不是**「凡术式相关伤害都必须重新造源」。判断一个伤害有没有归因，看 `getEntity()`/`getDirectEntity()` 有没有值，而不是看它有没有走 `deal`。
