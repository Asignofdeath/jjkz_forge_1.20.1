## 怪物韧性条：方案定案 + 阶段 0–2 落地

用户要求：EF 血条下面加一根白条；未破时霸体 + 减免一定比例伤害；破韧后移除增幅、赋予虚弱/易伤；
只有高级怪有（下限铁傀儡、劫掠兽，无上限）；咒力特质克制仅用于「特攻怪」的韧性条；
引入玩家 Break 效力可无视克制增幅破韧；**韧性条不是护甲、不吃穿甲**。

### 关键发现（我去 EF 源码核过，推翻了我自己先前的判断）
- ⛔ **EF 的盾不是所有怪都有**。`GlobalMobPatch extends HurtableEntityPatch<Mob>`（**不是**
  `LivingEntityPatch`）⇒ `getStunShield()` 恒 0、`setStunShield()` 空实现；`HealthBar` 只认
  `LivingEntityPatch`，所以通用怪**既没盾也没条**。真正能挂盾的只有
  `EntityPatchProvider:82-118` 登记的那 ~25 种。**监守者/潜影贝/远古守卫者都不在里面。**
- ✅ 但 EF 原生「盾 > 0 则免硬直」= **霸体是白送的**（`EntityEvents:203/222`），白条绘制也是白送的
  （`HealthBar:181/188`，y ∈ [-0.08, -0.0488]，正好贴在血条下面）。
- ⛔ **EF 的盾只挡硬直不挡伤害**（`HurtableEntityPatch:76` 是用 `impact` 扣盾，不是伤害）。
  所以「未破时减伤」必须自己加，且必须是**独立乘区**——走 `resistanceReduction` 会被
  `applyPenetration` 吃掉，那就成了「吃穿甲」。
- ⛔ `HealthBar.shouldDraw:46` 对 `forge:bosses` 直接返回 false（凋灵/末影龙连血条都没有）；
  `:75` 还要求「有 debuff 或掉血 或 是锁定目标」才画 ⇒ 满血未锁定时白条也不显示（已知限制）。
- ⛔ `setStunShield` 会 clamp 到 `[0, maxStunShield]` ⇒ **必须先 setMax 再 setStun**，反过来夹成 0。
- ✅ 时序安全：EF 从 NBT 恢复盾走 `MixinLivingEntity#readAdditionalSaveData`，早于
  `EntityJoinLevelEvent`，所以我们在 join 时设的值不会被覆盖。
- 将来给无 patch 的怪补盾：`EntityPatchRegistryEvent`（IModBusEvent，`EntityPatchProvider:122` 触发、`:125` 汇总）。

### 定案设计
- 复用 EF stun shield 当载体（同步/存档/白条全免费）；口径：**盾就是韧性**。
- 资格：显式 `poise` 块优先；没写则「体抗 + 术抗 ≥ 45」派生（45 正好把劫掠兽 45、铁傀儡 55 划进来）。
- 减伤档：45~59→15%，60~74→25%，≥75→35%。
- 公式：`poiseDmg = base × C × (1 + B_eff)`，其中 `B_eff = min(B,1.5) × (specialized ? 0.35 : 1.0)`。
  **C 与 (1+B) 必须同处一个乘法括号**——写成 `C + B` 会让克制直接归零。
- 破韧闸门（防「堆 Break 无视特质」）：克制命中→满档，仅靠 B 硬破→半档。
- B 软上限 +80%（超出收益减半）、硬上限 +150%；破损态 10s、期间韧性上限锁 30%。

### 落地（阶段 0–2）
新增 `entity/combat/PoiseStats`、`entity/combat/PoiseRules`、`event/MobPoiseEvents`；
改 `MobCombatStats`（+poise 字段 + 兼容旧 4 参构造）、`MobCombatStatsReloadListener`（解析 poise 块）、
`vanilla.json`（7 条：铁傀儡80/劫掠兽70/潜影贝90/远古守卫者110/监守者160/凋灵180/末影龙200）、
`TechniqueDamageZoneEvents`（**新增「区 4 · 韧性条减免」**）。
验证：`tools/jjkz_static_check.py` **578 文件 / exit 0 / 0 错误**。
⚠️ 阶段 1 只有 EF 已有 patch 的怪（铁傀儡/劫掠兽/凋灵/末影龙）会真的长出白条；
潜影贝/监守者要等阶段 6 自注册 patch。

## 怪物韧性条：阶段 3（破韧结算）落地

用户质问「为什么术式的技能伤害打不动韧性条，是你擅自规定的？」——**不是擅自规定，是漏了管线**。去 EF 源码核过：

- `EntityEvents.java:145`：`epicfightDamageSource = event.getSource() instanceof EpicFightDamageSource ? ... : null`
- `EntityEvents.java:195`：扣盾整段要求 `epicfightDamageSource != null`
- 本模组术式伤害是**原版 `DamageSource`**（`TechniqueDamageSources` 里 `new DamageSource(techniqueType(level), null, owner)`）⇒ **EF 整块跳过**。
- 连带：EF 自家近战也只扣 `impact`（`IMPACT` 属性默认 0.5，`HurtableEntityPatch:76`）⇒ 铁傀儡 80 点要砍 **160 刀**。
- 结论：**两个通道都扣不动**。阶段 3 必须由我们自己写。

### 落地
- `PoiseRules`：+`POISE_DAMAGE_BASE = 10.0`（每次命中固定扣，**与伤害量无关**——破韧必须是独立于伤害的进度轴，否则堆伤害的人顺手把所有怪的条秒掉）、`REGEN_DELAY_TICKS = 60`、`REGEN_INTERVAL_TICKS = 20`、`poiseDamage(poise, counter, breakPotency)`。
- `MobPoiseEvents`：
  - `onLivingHurt` @ **LOWEST**：玩家命中扣盾。挂 LOWEST 是为等区 4 改完 `amount` 再判断这一刀是否真落地；`LivingHurtEvent` 只在 `actuallyHurt` 内派发 ⇒ 天然滤掉无敌帧吞掉的重复命中。只认 `getSource().getEntity() instanceof Player`。已破（盾=0）时不再扣，留给阶段 4。
  - `onLivingTick`：空闲回复，满盾/已死/无盾时清理时间戳。时间戳用 `WeakHashMap<LivingEntity, Long>`（key 是**实体本身**不是 UUID）⇒ 卸载/消失后随实体回收，不用写卸载清理；`Entity` 的 equals 是同一性比较，正是所需语义。取模判断放最前，省掉每 tick 的能力查找。
- 手感：劫掠兽70→7刀、铁傀儡80→8刀、潜影贝90→9刀、远古守卫者110→11刀、监守者160→16刀、凋灵180→18刀。回复 4/s（部分 5/s），停打 3s 后开始回。
- 验证：`tools/jjkz_static_check.py` **578 文件 / exit 0 / 0 错误**。

### 遗留
- EF 系命中仍额外按 `impact` 多扣 0.5（约 5% 误差）；彻底夺权要自注册 patch 并 override `damageStunShield`（阶段 6）。同一步顺带解决监守者/潜影贝/远古守卫者拿不到条。
- 阶段 4（破损态 10s + 虚弱/易伤）、阶段 5（特质克制表 + Break 效力面板）未做。

### 环境坑（新）
- ⛔ **PowerShell `*>` 重定向会把子进程输出重新编码成 UTF-16**，且中文部分会经过一次 GBK/UTF-8 误判 ⇒ 结果文件必须 `raw.decode('utf-16')` 读，中文仍是花码，只能靠**数字位**判断（`exit = 0` + 末尾 `0` 双向印证）。别试图用 Read 直接看。
- ⛔ **Bash 的 `rm` 也挂了**（shim 缺 `dirname`，exit 127）。删文件用 Python `os.remove`。

### 教训
- ⛔ 我第一版把减伤裸写在 `MobPoiseEvents` 的 `LivingHurtEvent` 里，**违反了项目铁律**——
  `TechniqueDamageZoneEvents` 类注释第 74-76 行明确写着「后续新乘区（易伤、克制、标签抗性……）
  一律加进本类……不要再到别的监听器里裸写 setAmount 乘算」。**加新乘区前先读那个类的注释。**
- ⛔ 用户问「Break 会不会让克制无足轻重」时，我第一反应答错了方向：`C × (1+B)` 下**相对差恒为
  1.67× 不会被稀释**，真正的侵蚀是**绝对刀数差塌缩**（6 刀 → 1 刀）＋ **通用性打败局部性**的
  激励倾斜。别把「比例不变」当成「没问题」。

## 怪物韧性条：阶段 4（破损态）落地

### 定案（数值我先定，随时可改，全在 PoiseRules 一处）
- 触发判据：**这一击把「正数」的条打到 0** 才进破损态。破损期内继续命中**不刷新窗口**
  —— 不闸的话贴脸打就是永久破防，韧性条沦为一次性开关。
- 时长 `BROKEN_DURATION_SECONDS = 10` → `BROKEN_DURATION_TICKS = 200`。
- 虚弱 `BROKEN_WEAKNESS_AMPLIFIER = 1`（虚弱 II），时长与窗口一致。
- 易伤 `BROKEN_VULNERABILITY_POINTS = 25`：**从体抗 / 术抗各扣 25 点**（Attribute 层，
  专用 UUID `…-3005/3006`，`Operation.ADDITION`，负值）。这是本模组「易伤」的既有落地方式
  （`ModAttributes` 注释已写「抗性允许负值（易伤）」，`SkillDefenseResolver` 对负抗性原样保留、不吃穿透）。
- 破损期内：上限锁 30%，盾清 0 且**禁止回复**，`damageReductionFor` 直接返回 0。
- 到期：恢复满上限，撤掉虚弱与易伤，盾从 0 正常回复。

### 一个必须记住的 EF 事实
⛔ **盾 == 0 时 `HealthBar` 直接 `return`（`HealthBar.java:176-178`），整根白条是「消失」而不是「空」。**
所以「破损期锁 30% 上限」**不是**视觉效果（盾为 0 时压根不画），它真实的作用只有一条：
兜底防止破损期内有别的代码路径把盾加回去、把霸体偷偷还回来。别在注释里吹它是视觉反馈。

连带推出「破损期内必须禁止回复」：EF 的霸体判据是 `盾 > impact`，回一点点霸体就提前回来，
「移除霸体增幅」这句话就成假的了。**霸体全程失效 = 盾全程为 0**，没有第二条路。

### 顺带修掉的一个真 BUG
阶段 3 漏了**末影龙豁免**：`vanilla.json` 里给末影龙写了 poise 200，`applyPoise` 会跳过它
（盾归 EF 水晶机制管），但 `onLivingHurt` / `onLivingTick` 没有对应的 `isEnderDragon` 闸
⇒ 会去扣 EF 的水晶盾、还会把它的上限锁到 30%。现在两处都加了 `isEnderDragon` 早退。

### 落地
- `PoiseRules`：+`BROKEN_DURATION_TICKS`、`BROKEN_WEAKNESS_AMPLIFIER`、
  `BROKEN_VULNERABILITY_POINTS`、`brokenShieldCap(double)`。
- `MobPoiseEvents`：+`BROKEN_UNTIL`（WeakHashMap，同 `LAST_PLAYER_HIT` 套路）、
  `enterBroken` / `exitBroken` / `clearBroken` / `applyVulnerability` / `removeVulnerability`
  （修饰符读写照抄 `MobCombatStatsEvents` 的 `setModifier`/`removeModifier` 写法）、
  `isBroken()`；`damageReductionFor` 破损态恒 0；`applyPoise` 开头 `clearBroken` 做自愈。
- `clearBroken` 以「`BROKEN_UNTIL` 里有没有本实体」为闸——它在**每个**生物入世时都会被调到，
  不设闸会把别人（药水等）挂的虚弱一起删掉。
- 验证：`tools/jjkz_static_check.py` **578 文件 / exit 0 / 0 错误**。

### 遗留 / 待定
- 破损态是「破一次给 10s 窗口」；持续贴脸打的结果是**条一直是 0（永久无霸体、无减伤）但虚弱/易伤
  只在前 10s**，想再拿一次得停手让条回一点再打。这条「节奏」是否合意，等用户拍。

### 克制表（权威定义写在 `CursedEnergyTrait` 类注释里，别在别处再抄一份）
- 相克环：**精 → 粗 → 属 → 精**；常不在环上，与谁都中性。
- 倍率：`COUNTER_ADVANTAGE = 1.25` / `COUNTER_DISADVANTAGE = 0.8` / `COUNTER_NEUTRAL = 1.0`。
- `PoiseRules.counterMultiplier(玩家特质, 怪特质)`；任一为 null、任一为常、同环外组合 → 1.0。

### 破韧质量闸门
`breakQualityFactor(counter, bEff)`：吃到克制 → 满档 1.0；没吃克制但有 Break 效力 → **半档 0.5**；
两者都没有（纯基础值磨破）→ 满档 1.0。**只削收益强度，不动时长**：
- 虚弱等级 `floor(1 × 0.5) = 0`（II → I）
- 易伤 `25 × 0.5 = 12.5` 点（小数没关系，属性本来就是 double）
十秒这个节奏固定，变的是这十秒里怪有多虚——便于玩家建立预期。

### Break 效力（`ModAttributes.BREAK_POTENCY`）
- 玩家专属属性，百分比点数，范围 0~150（上限对齐 `BREAK_POTENCY_HARD_CAP`）。
- `ModAttributes.breakPotency(entity)` 返回**原始比值**（值/100），**不做**软上限与特攻怪打折
  ——那两步在 `PoiseRules.effectiveBreakPotency` 里，别重复实现。
- 软/硬上限：软 +80% 内 1:1，超出部分折半，最后卡 +150%。

### 数据包拼写检查（这次的「启动自检」）
⛔ `CursedEnergyTrait.byId` 是宽容版（解析失败回落成常），**拿它读数据包会让 `"refind"` 这种错字
静默变成「不参与克制表」** —— 玩家只会觉得克制没生效却找不到原因。
所以新增 `CursedEnergyTrait.find(id)`（识别不了返回 null，`byId` = 它 + NORMAL 兜底），
数据包解析一律用 `find` 并 `LOGGER.warn` 明确报出可用值，报错后按「没写」处理（不误伤整份数据包）。

## 新 SE「掉钻的星形耳环」：芝诺墙改写 + 窄口即冲突声明

用户要做一个爱与幽会专用 SE：把跨序之星的芝诺墙换成施加力，「能推着别人走」。
他提出「以后又有 SE 要改芝诺墙会冲突，需要为每个 SE 配置冲突列表」。

### 我的判断：不上冲突列表，用窄口接口当改写点
冲突列表（`conflicts: Set<String>`）的致命问题是**不对称**——A 列了 B、B 没列 A 时，
**装载顺序不同结果不同**。而窄口接口天然对称、自动互斥、新增 SE 不用回头改旧的
（靠上一轮加的 `SeMechanicRegistry#hasNarrowInterfaceConflict`）。
⇒ 给「改芝诺墙」定义一个窄口 `ZenoWallSeMechanic`，将来的同类 SE 实现它即自动互斥。

**为什么之前 mutexGroup 一直是摆设**：现有三条 SE 全是**追加型**（点燃 / 加灌充来源 /
加远程目标），谁也没改写谁的既有机制，本来就不冲突。这条是**第一个改写型**，
所以冲突问题现在才冒出来——不是设计错了，是终于碰到真冲突了。
（代价叠加本身不冲突：`sumPenaltyAmount` 按 ApplyKind 累加，两条都削体抗就是 −x−y，良定义。）

### 关键源码事实（都核过，不是记忆）
- 芝诺墙 = `StarMarkRules.zenoWall()`（2052 行），是**位移域**硬约束，不是力。
  2027-2031 明确写了当初为什么刻意选位移域：速度域「比谁力气大，持续输出能净推进」，
  位移域「指数逼近、永不抵达」。⇒ 这个 SE 是在**反转一个刻意的架构决定**。

  ⇒ 「整对替换」的判据是**施术者装载与否**（墙是星域的属性，不是被推者的属性）。
- `push()`（2149 行）签名 `push(Entity, Vec3 impulse, ServerPlayer owner, boolean allowOwner)`，
