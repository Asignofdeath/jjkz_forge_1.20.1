## 修复：IDEA 里点 runClient 弹出「编辑配置」对话框

诊断结论（非代码问题）：
- `.idea/runConfigurations/*.xml` 是在**另一台机器**上生成的（Windows 用户 `25196`、H 盘），4 个配置里各有 3~5 处 `H:\MineMOD\...`、8~9 处 `C:\Users\25196\.gradle\...`。
- 模块名悬空：配置写 `JuJutsuKaisenZone_forge-1.20.1.main`，而 9/21 重新导入后实际模块是 `JuJutsuKaisenZone_forge-1_20_1.main` → IDEA 判定配置不完整，点运行只弹编辑框。
- `build/classpath/*.txt` 内容也全是 `C:\Users\25196\.gradle\...` 的 jar（116 行）。
- 本机 `~/.gradle/caches/forge_gradle/assets` 此前不存在 → 本机从未跑起过客户端（`run/` 里的日志是旧机器留下的）。

根因（ForgeGradle 6.0.54 源码 `RunConfig.getIdeaModule()`）：
`project.getName().replace(' ', '_') + ".main"` —— **只换空格，不换点号**；而 IDEA 导入 Gradle 项目时会把项目名里的点号换成下划线。Gradle 项目名取自目录名，本项目目录名 `JuJutsuKaisenZone_forge-1.20.1` 带点 → 两边必然不一致，每次重新生成都会错位。

处置：
1. `.idea/runConfigurations/*.xml` 先备份到 `/tmp/runConf_backup_20260922/`。
2. `settings.gradle` 末尾加 `rootProject.name = 'JuJutsuKaisenZone_forge-1_20_1'`（去点号，与 IDEA 模块名对齐）。
3. `./gradlew genIntellijRuns --project-cache-dir=build/.gradle-tmp`（约 2 分钟，连带跑 `downloadAssets` / `createSrgToMcp` / `extractNatives` / `prepareRuns`）。
4. 结果核对：4 个配置模块名均变为 `JuJutsuKaisenZone_forge-1_20_1.main`，路径全部指向 `C:\D\...` 与 `C:\Users\19316\.gradle\...`，无旧路径残留；`build/classpath/*.txt` 全部重写（116×19316，0×25196）。

注意：改完必须在 IDEA 里 File → Reload All from Disk（或重启 IDEA），否则内存里的旧配置可能把文件覆盖回去。另外 4 个配置原有的 Make + `:prepareRunClientCompile` 前置任务保留不变。

## 把调节模式的三个按键注册成可改键

新增 3 个 KeyMapping（定义在 `event/TechniqueSkillKeyEvents`，在 `JuJutsuKaisenZone.ClientModEvents.onRegisterKeyMappings` 里注册）：

| 字段 | lang key | 默认 |
|---|---|---|
| `KEY_ADJUST_MODE` | `key.jujutsukaisenzone.adjust_mode` | 鼠标中键 `GLFW_MOUSE_BUTTON_3`（注意 GLFW 里 `_BUTTON_3` == `_MIDDLE` == 2） |
| `KEY_ADJUST_TIER_DOWN` | `key.jujutsukaisenzone.adjust_tier_down` | 鼠标侧键 4 |
| `KEY_ADJUST_TIER_UP` | `key.jujutsukaisenzone.adjust_tier_up` | 鼠标侧键 5 |

原来的 `GLFW.glfwGetMouseButton(...)` 裸轮询换成 `KeyMapping.isDown()`。lang 在 zh_cn/en_us 的同位置各加 3 条。

### 已核实的 Forge 1.20.1 机制（反编译源码 `forge-...-sources.jar`）
- `MouseHandler.onPress` 里 `KeyMapping.set(InputConstants.Type.MOUSE.getOrCreate(i), flag)` **只在 `screen == null && overlay == null` 时**执行 → 鼠标键用 `KeyMapping.isDown()` 是安全的（我们的 tick 本来就要求无界面）。
- `KeyMapping` 构造函数自身就 `ALL.put(name,this)` + `MAP.put(key,this)`，`resetMapping()` 由 `Options.load()` 重建 → `isDown()` 不依赖注册事件。
- `KeyMapping.isDown()` = `isDown && isConflictContextAndModifierActive()`；`KeyConflictContext.IN_GAME.isActive()` == 无界面，正好与我们的守卫一致。
- **`RegisterKeyMappingsEvent.register(key)` 的真实作用**是 `options.keyMappings = ArrayUtils.add(options.keyMappings, key)`（`Options.keyMappings` 决定控制界面列表与 options.txt 持久化）。所以**必须**走这个事件，光 new 出 KeyMapping 只能让 `isDown()` 生效、不会出现在控制界面。

### 顺带发现（未修）
`client/BarrierRulesKeyHandler`（结界规则，B 键）的 `@Mod.EventBusSubscriber(modid, value = Dist.CLIENT)` **没写 `bus = Bus.MOD`**，默认是 FORGE 总线，而 `RegisterKeyMappingsEvent` 是 mod 总线事件 → 它的 `registerKeyMappings` 是死代码，`key.jujutsukaisenzone.barrier_rules` 不会出现在控制界面。该文件同时还有 FORGE 总线的 `onClientTick`，所以修法不是加个参数那么简单，得把注册挪到 `ClientModEvents`（或拆成两个类）。

## 修复：说明节点不应有连线

症状（用户报）：术式开发界面里「说明节点」（INFO，如 `limitless_domain_muryokusho` / `judgment_sinful_one` / `shrine_domain_fumoshinkan`）也带着连线。

根因：说明节点在声明时用了 `.requires(<锚点技能>)`（4 处），而 `prerequisiteNodeIds()` 是**双用途**的——
被 `SkillTreeLayoutEngine` 用于算列深与 barycenter 排序（**布局锚点**），同时被 `SkillTreeConnectionsWidget` 直接拿来画线。
后者是错的：说明节点不参与解锁前置（`SkillUnlockLogic.arePrerequisitesMet` 只在 `isSkillNode()` 路径上跑；也没有任何技能以说明节点为前置）。

处置（**保留 `requires` 作布局锚点**，只切断「连线 / 连通」语义）：
1. `SkillTreeNodeDef` 新增 `static boolean isConnectableEdge(from, to)` —— 任一端是 INFO 节点即为 false；
   同时给 `requires()` 写明「技能=解锁前置会画线 / 说明节点=布局锚点不画线」。**规则只此一处**。
2. `SkillTreeConnectionsWidget.drawInBackground` 第一遍绘制加该判定（`sourceWidget` 与 `node` 两端都覆盖）。
3. `TechniqueDevelopmentCanvasWidget.computeHighlight` 跳过 INFO 节点、跳过 INFO 前置，并在 `selectedNodeId` 本身是 INFO 时不再收后继
   （否则会出现「高亮成一组却没有线」的怪状态）。
4. 编译：`BUILD SUCCESSFUL`。

⚠️ 说明节点因此变成**只靠邻近位置表达归属**（仍在锚点右侧一列、行序贴近锚点），没有线。用户若不满意再谈布局。

   吃同一份 30 秒冷却）。这与「免费条目必须前置分流」是同一套判断的两个方向：**要扣费的放行、免费的拦截**。

## 统一修复：特别招式「白扣咒力」（基类前置收口）★

根因只有一条：默认链路 `useSpecialMove(skillId, mask)` 无条件先 `castWithSkillEconomy(原技能)`（扣咒力 + 上冷却），
之后才轮到 `castSpecialMoveBySkill` 演出 → **「这个修饰键组合到底有没有实现」判在了扣费之后**，判晚一步就是白扣。

实际白扣面比原记忆里记的更宽（本轮核查）：

| 技能集 | 白扣场景 |
|---|---|
| `Limitless` | 掩码收口写在 `castSpecialMoveBySkill` 里（已在 `castWithSkillEconomy` 之内）→ Ctrl / Alt / Shift+Ctrl + 1/2/3 白扣；**变体未解锁时 Shift+1/2/3 也白扣**（独立解锁字段查得同样晚） |
| `Shrine` | `castSpecialMoveBySkill` 是空的覆写 → 任意修饰键 + 任意数字键 → 全额扣费 + 上冷却，连提示都没有 |
| `Judgment` | 完全没有特别招式代码 → 同上 |
| `LoveRendezvous` | ✅ 已正确（`useSpecialMove` 前置分流） |

修法（4 文件，`BUILD SUCCESSFUL`）：
1. `AbstractInnateTechniqueSkillSet.useSpecialMove` 在 `castWithSkillEconomy` **之前**插两道收口，并新增两个 protected 钩子：
   - `acceptsSpecialMove(player, skillId, mask)`：默认 = `getSpecialMoves(skillId)` 里**掩码精确相等**的声明
     （所以声明 Shift 不会顺带放行 Shift+Ctrl）；找不到 → 静默 return，不扣费。
   - `isSpecialMoveUnlocked(player, skillId, mask)`：默认 `true`（原技能解锁归 `castWithSkillEconomy` 管）；
     返回 false → 统一提示「该招式尚未解锁。」后 return，同样不扣费。
2. `Limitless`：`castSpecialMoveBySkill` 缩成三行 switch（纯演出），删掉掩码检查与三个变体解锁检查；
   改覆写 `isSpecialMoveUnlocked` 承接三个独立解锁字段。（提示文案由「该变体招式尚未解锁。」统一成基类的「该招式尚未解锁。」）
3. `LoveRendezvous`：覆写 `acceptsSpecialMove` 单独放行 `star_mark` 的 SHIFT / CTRL——这两个是
   「复用原技能行为、不进开发树」的输入，不在 `SPECIAL_MOVES` 声明里，不覆写就会被第一道收口静默拦下。
4. `Shrine`：删掉空覆写、留注释；`Judgment` 零改动（无声明 → 自动被拦）。

⚠️ **新硬约定：「先声明，后执行」**——新增特别招式必须**同时**在 `getSpecialMoves(baseSkillId)` 里声明，
只写 `castSpecialMoveBySkill` 分支等于这个组合不存在（表现为按了没反应，而不是白扣费）。
免费 / 条件性放行的条目仍要覆写 `useSpecialMove` 抢先分流，并**一并覆写 `acceptsSpecialMove`**，
否则会（而且必须）在第一道收口被拦下。两条都已写进基类与接口 javadoc。

## 「原地星域没特效」——渲染被「无标记」提前挡掉

现象：Shift + 禁行按下去，只弹文字、看不到环。
根因不在特别招式链路（那条已通：`SPECIAL_MOVES` 声明 → `acceptsSpecialMove` 放行 → `castSpecialMoveBySkill` → `activateFixedGate`），
而在 `StarMarkRules.apply` 开头 `if (marks.isEmpty()) return;` —— **星域外环的 `spawnRing` 循环写在方法尾部**，
所以「身上一个标记都没有」时，力学没得算，环也跟着一起被吞掉。跟随版当年同样如此，只是圆心在自己脚下不易察觉。

修法（`StarMarkRules`，`BUILD SUCCESSFUL`）：
1. `apply` 开头先算 `level / now / ownerPos / gateCenters`，再判空；空标记时**只画环**后 return。
2. 抽 `private static void renderGates(level, owner, gateCenters, now)`：空圆心或不在 `RENDER_INTERVAL_TICKS` 周期内就返回，
   否则按当前标记类型给每个圆心画一圈。尾部那段内联循环改为调它。
3. `apply` javadoc 补一句：表现与标记解耦，环只由「域是否生效」决定。

⚠️ 记住这条约定：**星域的表现跟着「域」，不跟着「标记」**；以后再加域类效果，别再让它挂在 `marks` 的非空分支里。

⚠️ 环境坑：无 `--offline` 的 gradle 会因拉不到仓库卡到 1h49m 才 `BUILD FAILED`（同时间报 `ENOTFOUND copilot.tencent.com`），
**编译一律加 `--offline`**，1~2 分钟出结果，别被这种超时误导成代码错误。

## 星域尺寸托管给「结界尺寸调节器」
