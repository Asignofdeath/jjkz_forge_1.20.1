## 防御乘区：体术抗性 / 术式抗性 + `jjkz:technique` 伤害类型

用户给「体抗」定死语义：**只吃 EF / 原版怪物近战 / 本模组体术**，不碰箭 / 爆炸 / 火等原版通道。术抗只吃术式。

### 落地
- 新建 `registry/ModAttributes.java`：`PHYSICAL_RESISTANCE` / `TECHNIQUE_RESISTANCE` 两个 `RangedAttribute`（**单位是百分比点数**，-100~100，`setSyncable`）；`EntityAttributeModificationEvent#getTypes()` 返回 `List<EntityType<? extends LivingEntity>>`，`add` **不做重复检查**，我们自己加所以安全。默认值 0 ⇒ 怪物近战不会凭空变软。
- 新建 `technique/JjkzDamageTypeTags.java`（`IS_TECHNIQUE`）+ `technique/SkillDefenseResolver.java`（护甲 / 体抗 / 术抗三层换算，与 `SkillDamageResolver` 对称）。
- 数据包：`data/jujutsukaisenzone/damage_type/technique.json`（`message_id = "jjkz.technique"`，注意带点）+ `tags/damage_type/is_technique.json` + `data/minecraft/tags/damage_type/{bypasses_armor,bypasses_shield}.json`。**故意不加** `bypasses_resistance` / `bypasses_enchantments` / `witch_resistant_to`。
- `TechniqueDamageSources`：新增 `TECHNIQUE_DAMAGE_TYPE`（带 holder 缓存，按 `registryAccess` 失效）+ `techniqueSource(level, owner)` + `isMelee(DamageSource)`；`deal` 的两处 `magic()` 全换成新类型。茈 / 远程茈 / 灶 三处 `mobProjectile` 收口成 `techniqueSource`。
- `TechniqueDamageZoneEvents`：分型解析**解除 `ServerPlayer` 绑定**（怪物近战要能分出体术，否则体抗对怪物无效）；区 2 改成「护甲（仅 `IS_TECHNIQUE` 通道，自研线性公式）→ 抗性（复合各半，两层乘算）」；区 3 ZONE 减伤原样保留。
- Config：新增 `combatDefense.*` 7 项（enabled / armorFactorPerPoint 2.0 / armorMaxReduction 60 / physicalResistanceCap 70 / techniqueResistanceCap 70 / defenseReductionCap 85 / compositeResistanceShare 0.5）。
- `JjkzPlayerDataDisplay` 补一行「护甲（防御力） / 体术抗性 / 术式抗性」；lang 中英各 3 键。
- 区 0 扩到 `MARTIAL || COMPOSITE`：**复合在近战里只有两条路** —— 「EF 基础攻击 + 必定黑闪」（要倍率）与「处刑人之剑必杀」（不能要）。后者伤害量已在 HIGHEST 被改写成固定致死值，再乘面板倍率会让低强度玩家杀不死 ⇒ 用 `!isExecutionersComposite(...)` 精确排除，与分型解析同一判据。

### 关键认知
- **`DIRECTENTITY == getEntity()` 是近战的正判据**，比查标签准，也不依赖 EF；`fallingBlock` 这类 directEntity 不是生物，被 `instanceof LivingEntity` 天然排除。
- **术式必须自研护甲公式**：原版 `CombatRules.getDamageAfterAbsorb` 的减免率与伤害量强相关，8 点小伤害对钻石甲约 −72%，而术式多是「每 1~5 tick」的高频小伤害，继承原版等于把高频流派整个打死。
- **强乘算的减伤不改变数值、只影响封顶**（`1−(1−a)(1−b)` 可交换）⇒ 体抗放在原版护甲之前 / 之后对结果无影响，但「总减伤上限」想跨过原版护甲层封顶就做不到。
- **遗留缺口**：`defenseReductionCap` 只在区 2 内部生效。体术通道的原版护甲在原版护甲层（区 2 之后）才结算 ⇒ 最坏情况 70% 体抗 + 钻石甲 80% = **94% 总减伤**，超出设计的 85%。要真正封顶只能把抗性层挪到 `LivingDamageEvent`（全部减免之后）或下调体抗上限。

## 静态类型检查终于跑通了（重要）

之前的痛点是「不能跑 gradlew」+「无 classpath 的 javac 全是误报」。现在有了一条**不碰 `build/`、不进 Gradle、20 秒出结果**的路子：**直接用 javac 编译整个 `src/main/java`（446 文件）**，classpath 从 gradle 缓存现场拼。见 `REFERENCE.md` 的「静态类型检查」一节。本次改完实测 **exit 0 / 0 错误**，是「改动是否落地」最硬的证据。
- ⚠️ 最大的坑：gradle 缓存里有 **11 个含 MC 类的 jar**，映射风格各不相同（srg / official / parchment / recomp…）。**只有一个是对的**：`minecraft_user_repo/net/minecraftforge/forge/1.20.1-47.4.10_mapped_official_1.20.1/forge-1.20.1-47.4.10_mapped_official_1.20.1.jar`。其余全要按「含 `net/minecraft/network/chat/Component.class`」这个特征排除，否则 SRG 名 jar 抢先命中的结果是 **6000+ 条假错误**（`Component` 上没有 `literal`、满屏 `m_xxxx_`）。
- ⚠️ 待删除 mcp 空壳：路径含 `mergeMappings` 或体积 < 2KB 的 jar 会让 javac 直接 `zip END header not found` 退出。
- ⚠️ classpath 太长（300 jar）会 `WinError 206 文件名或扩展名太长` ⇒ 必须把 `-cp` 也写进 `@argfile`。argfile 里路径用**正斜杠 + 双引号**（javac 把反斜杠当转义）。
- ⚠️ 用户可能在 IDEA 里**同时编辑**同一个文件：第一次跑出 1 个错误，事后查 mtime 发现是**检查当时正在被写**（差 25 秒）。报「编译错误」前先看 mtime，别把别人正在打的字当成自己的 bug。
