## 飞行物出伤性能改造 · 第一处：「解」挥砍（ShrineKaiArrowBehavior）
- **问题本质**：飞行物 behavior 把「伤害判定频率」绑死在「采样频率」上。解最坏：每 tick 飞 10 格（`ARROW_SPEED`）× 柱高 8 采样点（`COLUMN_HEIGHT`）= **80 次 `getEntitiesOfClass` + 80 次 `deal`/tick**，而其中 90%+ 会被原版 `invulnerableTime` 吞掉（`LivingHurtEvent` 只在 `actuallyHurt` 内派发）⇒ 纯浪费。
- **改造（只动 `ShrineKaiArrowBehavior` 一个文件）**：
  - `tick()` 内收集每格柱基点 `columnBases`；走完（含 `arrive()` 早退路径）在 `finally` 里统一调 `resolveAndSettleHits`。
  - 伤害判定：**整 tick 一次** `getEntitiesOfClass`，查询盒 `sweepBox` = 路径 AABB 按柱方向展开（竖斩向 up 展 8、横斩沿水平垂直方向 ±4）再 `inflate(COLUMN_RADIUS)`；候选集在下面按球逐点精筛。
  - `Set<LivingEntity> hit` 去重：**同一目标本 tick 只 deal 一次**。
  - `ShrineSkillGrowth.kaiColumnDamage` / `resolveOwner` 从「每采样点一次」降为「每 tick 一次」。
- ⛔ **判定逻辑与采样点集合一字未改**（同柱方向、同 `from..to`、同 `GeometryUtils.aabbIntersectsSphere` 球-盒判定）⇒ 命中范围不变。唯一行为差异是同 tick 重复命中由「deal 多次」变「deal 一次」，而重复的本来就被 `invulnerableTime` 吞 ⇒ **结算等价**。
- ⛔ **破方块链（`breakBlocksAtSample`）本轮未动**：它控制破坏范围，改遍历方式会变形状/玩法。仍是每采样点 5³=125 次迭代。下一步候选：① 合并两次 `getBlockState` 调用（零风险）；② 扫掠体一次遍历（**会改破坏形状，需用户拍板**）。
- **剩余 17 个 behavior 未动**：B 类定点体积（如超远程茈 `:559`）本来就只 1 次查询，性价比低；A 类专业飞行体（赫箭、茈箭、法槌、解的 flyobj 段）同类，可按同一手法逐个改。
- 验证：全工程 javac = 724 文件 / exit 0 / 0 错误。
- ⚠️ `ShrineKaiFlyobjBehavior` 有自己的私有 `tickColumn`，与本次改的不是同一处，别混。

## 飞行物性能改造 · 第四处：「解」破方块链升级到**档 B**（唯一会改破坏形状的改动）
- 用户随后拍板做档 B。两个文件同改：`breakBlocksAtSample` / `breakBlocksAtColumnSample` 整块替换为 **`breakBlocksInColumn`**，新增静态 **`cubeIntersectsCapsule`**。
- 做法：不再「每采样点各遍历 `(2r+1)³ = 125` 个立方体」，改成**整条柱只遍历一次** —— 先取柱轴线段（竖斩 `[base, base+up*(H-1)]`；横斩 `[base∓dir*H/2]`），`new AABB(a,b).inflate(COLUMN_RADIUS)` 得包围盒，逐方块判定「到轴线段最短距离 ≤ r」（方块中心投影到轴 → 球-方块判定，与 `GeometryUtils` 同一套判据）。
- ⛔ **这是本项目唯一一次改变破坏形状的改动**：覆盖从「8~9 个离散球并集」变成「轴上连续胶囊」。因球心间距 1 < 直径 3、重叠很深，**两端点完全一致**，只有柱腰部约 `r - sqrt(r²-0.25) ≈ 0.086` 格外扩 ⇒ 侧面可能多破坏极少数方块。用户已知并接受。
- 收益：迭代 竖斩 ~1000 → ~160、横斩 ~1125 → ~180~360；`getBlockState` 同步降到约 1/2~1/3（不再有相邻采样点的重复查询）。
- ⚠️ **已用 `javap` 坐实**：`AABB(Vec3,Vec3)` 委托给 6 参构造器，后者内部 `Math.min`/`Math.max` **归一化** ⇒ 柱方向朝负轴时也不会得到无效盒。命令：`javap -p -c -cp <forge jar> net.minecraft.world.phys.AABB`。
- 验证：javac 724 / exit 0 / 0 错误。

## 无量空处「扫描波」· 灰化：「扫过即灰、收回即复原」

用户需求：**「让被圈扫过的地方呈现灰色，圈收回经过时再复原」**。只改 `shaders/program/domain_scan_wave.fsh`（**纯资源改动，不涉及 javac**），3 处编辑。

**核心公式**（`dist` = 该像素反投影出的世界坐标到球心的距离）：
```glsl
float covered = 1.0 - smoothstep(0.0, band * 1.2, dist - Radius);   // 球内 = 已扫过
float luma = dot(base, vec3(0.299, 0.587, 0.114));
vec3 color = mix(base, vec3(luma), covered * GREY_STRENGTH * Intensity);
color += WAVE_TINT * add * 1.5;   // 环叠在灰化之后
```
- ⛔ **几何自洽，不需要任何额外状态**：扩张时球体变大（"已扫过"区域随之变大）、收回时球体缩小（像素依次退出球内自动复原）。半径本身就是唯一状态 ⇒ 不用记「扫过的快照」，也不用做时停那样的冻结深度。
- **顺序必须「先灰底色、再叠亮环」**：反过来环会被一起灰掉、失去冷白自发光感。
- **去饱和用「向亮度插值」而不是 `rgb2hsv` 降 S**：更便宜，且不会因色相环回产生偏色（JCraft 是走 hsv 的，我们只做灰化，不需要）。
- `GREY_STRENGTH = 1.0` = 完全灰度，想留一点色相调到 0.8 上下。
- 过渡带取 `band * 1.2`（落在环**外侧**），所以「复原」正好发生在圈收回经过该像素的瞬间，不会与环重叠导致闪。
- 灰化发生在 `AFTER_LEVEL` 的**后处理**里 ⇒ 只影响世界几何，GUI / 手持物不受影响。

验证：全工程 javac = **725 文件 / 292 jar / exit 0 / 0 错误 / 配置常量旁路 0**（资源改动理论不影响 javac，按惯例复跑确认）。

**待实机确认**：灰化观感与强度；贴地形 / 山体遮挡；峰值 128 格 × 70 tick 的节奏；`band = max(1.2, Radius*0.045)` 粗细；广播半径 24 格在峰值 128 时是否够。

## 无量空处「扫描波」· 球心改为每帧跟踪施法者脚底

用户反馈：**「扫描波中心看着不像从施术者的脚下发出的，看着像从施术者旁边」**。

**根因**：球心是服务端在 tick 20 发的**一次性快照**（`caster.getX/getY/getZ`，触发瞬间），而波要放 70 tick。前摇**不锁操作**（铁律），施法者一动，客户端渲染位置就与那个固定快照对不上 —— 越往后差得越多，看起来「不是从脚下发出的」。顺带还有 1 tick 的服务端位置陈旧（走速 ~0.2 格）。

**改法：客户端每帧实时跟踪施法者脚底。**
- `SyncDomainScanWaveS2CPacket` 加 `UUID casterUuid`（encode/decode 里排在最前）；`VisualNetwork` / `ModNetwork` 的 `sendDomainScanWaveSync` 各加一个 `UUID casterUuid` 形参；`LimitlessDomainExpansion#broadcastDomainScanWave` 传 `caster.getUUID()`。

- ⛔ **不用 `getX/Y/Z` 而用 `getPosition(partialTick)`**：前者是当前 tick 的瞬时值，人走动时波心会一顿一顿；后者按 `partialTick` 在上一 tick 与当前 tick 之间插值，与相机口径一致。已从源码坐实 `Entity#getPosition(float)`（`Entity.java:1528`）= `Vec3(lerp(pt,xo,getX()), lerp(pt,yo,getY()), lerp(pt,zo,getZ()))`，**返回的就是脚底**。
- ⛔ 顺带坐实：`ClientLevel#players()` 返回 `List<AbstractClientPlayer>`，且**本地玩家也在其中**（`ClientPacketListener.java:418 / 1078` 有 `level.addPlayer(id, this.minecraft.player)`）⇒ 施法者是自己时也能找到，不用额外特判 `minecraft.player`。
- ⛔ **一般教训（已记入 `REFERENCE.md`）**：任何「以某个实体为中心」的世界空间后处理，球心/锚点都要**每帧跟踪实体**，别用一次性快照 —— 只要演出期间不锁操作，快照必然会漂。

改动面 5 个 Java 文件：`SyncDomainScanWaveS2CPacket`、`VisualNetwork`、`ModNetwork`、`LimitlessDomainExpansion`、`DomainScanWaveRenderer`（包 id 102 与 `VisualPacketRegistrar` 的注册段未动）。

## 暴击政策重估：废除「高频不参与暴击」判据，放行 7 个术式招式

**起点是用户的质疑**：「原版存在伤害间隔，所以我们不需要对技能做『不参加暴击』的限制，对吧？」——**结论是基本成立**，但不是「整个名单删掉」，而是**判据本身错了**。

**旧判据错在哪**（这是本次最重要的一条认知）：
- 旧理由写的是「术式里每 1~5 tick 出一次伤的招式很多 ⇒ 默认不放行」（`TechniqueDamageSources#critAllowed` 与 `CritSkillPolicy` 两份文档都这么写）。
- ⛔ **这条判据把「出伤调用频率」当成了「真实结算频率」**。原版 `hurt()` 里 `invulnerableTime > 10.0F` 的判定发生在 `actuallyHurt` **之前**，而 `LivingHurtEvent`（暴击乘区所在）只在 `actuallyHurt` **内部**派发 ⇒ 被无敌帧吞掉的命中根本进不了管线。
- 数量级：解一 tick 80~90 次 `deal`（10 格 × 8/9 采样），同一目标**真实结算上限却是 10 tick 一次（2 次/秒）**。苍 4 tick / 捌 5 tick / 茈·超远程茈·灶开 每 tick 球内 —— **全部被压到同一个 2 Hz**。频率根本区分不出它们。
- `dealCrit` 那条注释里的「逐 tick 掷骰的期望与单次掷骰无异，只是方差被平均掉」**也说反了**：逐击独立掷骰的期望增幅与击中次数无关（线性），只有方差会降；而被无敌帧节流之后连「平均」都谈不上。
- **有主见的副作用**：`invulnerableTime` 是**实体级共享**的（不按伤害来源分），别人的箭 / 火 / 摔落会抢窗口 ⇒ 落地次数不稳定。但它只会让暴击**变少**，不会变多，所以不构成拒绝理由。
- 兜底确认：全仓 `bypasses_cooldown` / `BYPASSES_COOLDOWN` = **0 处**；`.setHealth(` 的调用点全是初始化 / 回血 / 仪式 / 血量表，**没有任何技能靠直接改血绕过 `hurt()` 出伤** ⇒ 「无敌帧会兜住」这个前提当前是干净的。**如果哪天挂了 `bypasses_cooldown`，本结论立刻失效。**

**现行判据（写进 `CritSkillPolicy` 类文档）只有两条**：①分型没有暴击资格（`CritRules#canCrit` 只放行 MARTIAL / TECHNIQUE，COMPOSITE 刻意排除：处刑必杀是致死量改写）；②结算语义特殊。

### A · 强制暴击标记的跨技能串味（放行的前提，必须先修）
- 机制：`CritRules.forceNext` 是一份**玩家级**待消费标记（唯一生产者 = 十划弱点击破），而 `applyCritZone` 的 `critAllowed` 闸门排在 `consumeForced` **之前** ⇒ 本击若不能暴击，标记**不会被消费、会悬挂到后续某一击**。
- 今天的状态：术式默认不放行 ⇒ 悬挂的标记只会被后续**体术**吃掉，而 `isRatio(player)` 玩家的体术命中基本就是十划自己的攻击 ⇒ 侥幸没暴露。
- 放行术式后：苍 / 解 / 茈 的命中都能消费它，会把 `RatioSpotLogic.forcedCritMult`（**1.50 起**，且是为十划标定的固定倍率）送给别的招式。
- **修法（最小改动）**：`TechniqueDamageZoneEvents#maybeForceRatioSpotCrit` 加一个形参 `SkillDamageType type`，注入前先 `if (!TechniqueDamageSources.critAllowed(type)) return;` ⇒ 「注入」与「消费」必然同击发生，标记不再跨击存活。
- **被接受的副作用**：本击不能暴击时不再击破弱点，光点留给后续可暴击的一击（原来是「击破并囤标记」）。
- `CritRules#forceNext(ServerPlayer, float)` 的 javadoc 补了不变量：「调用方必须保证注入的标记当击会就被消费，新增生产者照做」。

## 暴击跳字后缀「💥」：靠「暴击版 message_id」换样式

**需求**：暴击的伤害数字后面加个 💥。

### 为什么不能走「选择器判暴击」
把对方 jar 反编译（`javap -p -c`）坐实了三件事：
- `SelectorConfig` / `MatchRule` 里确实有个伪类型 `"critical"`（字节码 `ldc #118 // String critical`），但 `DamageEventListener.isCriticalHit` 是**写死的原版摔落暴击**：`source.getEntity() instanceof Player p && !p.onGround() && p.fallDistance > 0 && !p.isInWater() && !p.isPassenger() && !p.isFallFlying()` ⇒ **本模组的暴击系统影响不到它**，这条路彻底封死。
- `isPseudoType` 只有 `{kill, heal, absorption}`，所以 `.match("critical")` 也接不上自定义分型。
- `StyleBuilder` 有 `.suffix(String)` / `.icon(String)` / `.iconPosition(String)`，`Style` 是 record（`prefix`/`suffix`/`icon`/`iconPosition`/`killText`）⇒ `.suffix(" 💥")` 是真·追加文本，可用。

### 方案：暴击成立时把 message_id 换成 `.crit` 结尾
与项目既有叙事展示架构同形（`.match(message_id).style(...)`）。
1. `TechniqueDamageSources` 新增 `MSG_CRIT_SUFFIX = ".crit"`、`MSG_TECHNIQUE_CRIT`、`MSG_MARTIAL_CRIT`。
2. 新增 `markCritDisplay(DamageSource)`：读 `source.getMsgId()` 拼后缀，写进**已有的** `DISPLAY_MSG_OVERRIDE`（per-source ThreadLocal）⇒ 复用 `LivingDamageEvent` LOWEST 的自动清空时机。幂等（`.crit` 结尾直接返回，不会叠成 `.crit.crit`），受 `ModRules.StylizedDamageStyles.isEnabled()` 总闸门约束。
3. `TechniqueDamageZoneEvents` 区 C：`applyCritZone` 之后再读 `HitCritState.wasCrit()`，成立则调 `markCritDisplay(source)`。
4. `StylizedDamageCompat`：注册 `STYLE_MARTIAL_CRIT` / `STYLE_TECHNIQUE_CRIT`（外观同基础样式，只多后缀；术式那版连 ✦ 一起保留 ⇒「数字 ✦ 💥」），选择器链里把 `.crit` 规则排在基础规则**之前**。`MSG_*_CRIT` **直接引用** `TechniqueDamageSources` 的同名常量，杜绝生产/消费两侧字符串漂移。

### ⛔ 踩到的坑：`NarrativeDamageSource` 把 Mixin 挡掉了
`NarrativeDamageSource` **覆写**了 `getMsgId()`（不调 super、不读 `DISPLAY_MSG_OVERRIDE`），而 `DamageSourceMixin` 注入的是**父类**那一个 ⇒ 覆写会完全遮住 Mixin，走 `deal` 通道的伤害源**永远看不到暴击版 msgId**。已在 `NarrativeDamageSource#getMsgId()` 里先读 `peekDisplayMsgId(this)`、为空才回落到 `narrativeMsgId`。叠加层只活一次 `hurt → LivingDamageEvent`，栈外（死亡播报读键）拿到的仍是原值，不会把 `death.attack.jjkz.technique` 改坏。

## 自写配置层（用户需求：「让模组作者集中改数值，高级用户也能改」，只要两件事）

> 本节的部分结论**覆盖**上面「配置系统去文件化」那节的措辞：上一节写的是「本模组已无配置文件」，
> 那是**中途状态**；现在有配置文件了，但它只是**覆盖层**，代码默认值仍是权威。

### 需求与定案
用户原话：只需要非常简单的两件事 —— ① 让模组作者能集中改数值；② 高级用户也能改。明确说「不需要很复杂」。
用户随后「照方案做」。批准的设计要点：`ForgeConfigSpec` **只留值容器那一半**，文件读写那半（`ConfigTracker` /
`ConfigFileTypeHandler` / `ConfigWatcher`）整个扔掉，自己写文件层。两个我提的建议按推荐采纳：
**(1) 机制开关不开放给玩家改；(2) 越界值夹回范围内 + 警告。**

### 为什么能这么拆（关键发现）
Forge 的 `ForgeConfigSpec` 本来就是两半：
- **值/校验容器**（`defineInRange` 的默认值、范围、注释）—— 有价值，留着；
- **文件 I/O**（`ConfigTracker` 加载后立刻 `save()` → `Files.newOutputStream` **先截断成 0 字节**再写、
  非原子 → 异步 watcher 可能读到半写文件 → 判错 → 备份 + 用默认值重写）—— 病根，扔掉。
- 另一条线索：`ForgeConfigSpec#setConfig()` **只在 config 是 `FileConfig` 时才 `save()`**
  ⇒ 纯内存的 `CommentedConfig` 完全不触发那条截断路径。这是我们敢绕开的依据。
- `correct()` 不能用来自动纠正玩家文件：它第二步会**删掉未知键** ⇒ 对手改文件是破坏性的。所以**自己写行解析**。
- NightConfig 在本项目**不是声明依赖**（`src/main/java` 无引用、`build.gradle` 无 `night` 条目）⇒ **不引入依赖**。

## 联机时以服务端配置为唯一真相（用户要求，2026-10-03）

用户原话：「需要处理一下联机游戏中的情况，在联机游戏中，应当以房主或服主的配置文件为唯一真相。」

### 先查清的两件事（决定了方案的形状）
1. **客户端根本不读本模组的 `Config`**。全工程 17 个 `import ...jujutsukaisenzone.Config` 的文件里，
   `client/` 下只有 1 个 —— `client/gui/technique/PlayerDataPanelWidget.java:13` —— 而且是**未使用的残留 import**
   （全文再无 `Config.`）。其余 3 个 client 文件引的是 `ShrineFugaConfig` / `LimitlessRemoteMurasakiConfig`
   （Java 常量类）与 EpicFight 的 `ClientConfig`。
   ⇒ **玩法本来就是服端算的，联机不存在实际分叉**。方案的意义是让「客户端静态字段 == 服务端」这条不变量成真，
   并防将来加客户端读取时静默分叉。
2. **真 bug 在「先连服、再进单人」**：`Config` 的静态初始化一个 JVM 只跑一次，
   ⇒ 进单人存档时不会重读文件，会继续沿用**服务器下发的值**。所以「断开时还原」不是锦上添花，是必需。

### 实现（3 个新文件 + 4 处改动）
| 文件 | 改了什么 |
| --- | --- |
| `config/CfgSpec.java` | 加 `ConfigValue.serialize(T)`（与 `parse` 严格互逆）、`serializeEffective()`、`resetToDefault()`；加 `CfgSpec.exportOverridable()` 与 `resetOverridableToDefaults()`。字符串一律**带引号**输出（否则首尾空格被 strip、值里的 `#` 被当注释）。 |
| `Config.java` | 加 `LOGGER` 与三个 `public static`：`exportServerOverrides()`、`applyServerOverrides(Map)`（**先 reset 再套用**）、`reloadFromLocalFile()`。 |
| `network/packet/SyncModConfigS2CPacket.java` | **新**。`Map<String,String>` 载荷；handle 里 `hasSingleplayerServer()` 时直接 return。 |
| `network/api/PlayerSyncNetwork.java` + `network/ModNetwork.java` | 加 `sendModConfigSync` 门面；**`PROTOCOL_VERSION` `"1"` → `"2"`**。 |
| `network/registration/PlayerPacketRegistrar.java` | 注册 **ID 105**（0~104 已用满且无重复，105 是下一个空闲）。 |
| `event/ConfigSyncEvents.java` | **新**。`PlayerLoggedInEvent` → 推送，并仿 `CursedEnergyEvents` 在下一 tick 重发一次。 |
| `client/ClientConfigSyncHandler.java` | **新**。`ClientPlayerNetworkEvent.LoggingOut` → `Config.reloadFromLocalFile()`。 |
| `config/ConfigFileLayer.java` | ⛔ **修 bug**：`apply()` 开头加 `spec.resetOverridableToDefaults()`。 |

### ⛔ 抓到的真 bug（harness 立了大功）
第一版跑 `RealSyncHarness` 第 4 步失败：
```
[FAIL] 恢复本地默认 32   实际=64  期望=32
```
根因：`CfgSpec.apply(Map)` 是**按键改写**，不是整体替换 —— 文件里没写的键**保留原值**。
本地 `settings.toml` 模板 88 项几乎全是注释行，只有 1 行生效 ⇒ 断开后重读文件，
剩下 87 项继续沿用服务端下发的值。**修法**：在 `ConfigFileLayer.apply()` 开头先
`spec.resetOverridableToDefaults()`（语义定为「本文件就是全部真相」），
`Config.applyServerOverrides()` 同样先 reset。
⇒ 复跑两个 harness 全绿。**教训：任何「用一份表去替换整个命名空间」的地方，都要先清空再灌。**

### 验证
- 静态自查：**728 文件 / 292 jar / exit 0 / 0 错误 / 配置常量旁路 0**（725 + 3 个新文件）。
- `SyncHarness`（纯 `CfgSpec`，不碰 MC）全绿：对齐 10 项、服务端没改的键本地残留被清掉、
  布尔与列表不进表、`serialize→parse` 往返无损（值里的 `#`、引号、反斜杠、首尾空格、空串、
  看起来像数字的字符串、`0.4000000059604645` 位级往返）、reset 回默认、空表套用 = 全默认。
- `RealSyncHarness`（**真实 `Config` + 真实 `settings.toml`**）全绿：本地 0.35/32 →
  导出 88 项 → 服务端下发 0.9/64 后业务字段确实改灌 → 断开后回到 0.35/32。
